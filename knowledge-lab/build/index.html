Reuse, repair, prove, extend ​

Before moving a useful-looking file, identify one behavior worth keeping and the test that will tell you whether it survived the move.

Share on LinkedIn

LinkedIn opens a draft you can review before posting.

A working function in an older project can save a team days. It can also carry an assumption that the new system cannot afford. Start with one behavior from Ordo, trace its source, and decide which observation would justify reusing it. Each stage below builds something small enough for a teammate to verify.

Start with evidence ​

The reuse map separates the historical Rust/SQLite daemon, current rebuild, executor lab and streaming workshop. The source audit pins files and symbols to exact revisions. The extraction plan defines the boundary before code moves.

Record the donor revision and the exact command you ran in your checkout. A test included with the donor tells you what someone intended to check. Your own run establishes what passed in this environment. Check reuse rights before taking any material from a private repository into a public lesson.

Take the historical job kernel in the source audit. Can a worker reuse its name and deliver a result from an older attempt? Run the Rust lease exercise. Record the donor revision you inspected, your Lab checkout revision, the test command and the observed result for rejects_old_attempt_even_with_same_worker_name. The exercise checks the acceptance rule in memory. A database race between two clients is a separate application test.

Work you can run now ​

From a checkout with Node.js 22+ and Python 3.10+:

sh
npm ci
npm test
npm run dev

These commands validate and serve documentation plus synthetic examples. They do not start the research backend. The separate Rust example command and compiler pin are in clean builds.

What every change carries ​

A requirement, a bounded issue, relevant donor references, tests, atomic commits and a review receipt. Use the acceptance register for stable IDs and the twelve-factor matrix for operating properties.

Build an identifiable artifact once. Run the tests against that artifact, then promote the same artifact with reviewed configuration. Record application release, library publication, and documentation deployment as separate outcomes so a successful site build cannot accidentally certify the application.

First implementation target ​

Extract DAG validation and idempotent job creation with transactional events. Exclude model calls, frontend work and live deployment. Follow with lease fencing and scoped replay before adding evidence extraction.
