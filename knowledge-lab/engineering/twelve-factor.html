Twelve-factor design, with explicit storage boundaries ​

Replace the API process in the middle of a conversation. Which records should still be there and who owns the disk that holds them?

Share on LinkedIn

LinkedIn opens a draft you can review before posting.

Suppose the hosted API is replaced during a deployment. A reader should still be able to recover their conversation and its citations. That expectation leads to a more useful question than whether the project uses containers. Which process may disappear, and which component owns a record that must survive?

The matrix applies the published twelve-factor model to the proposed API and workers. The portable local research library needs an explicit storage exception. Each row is an acceptance test for a future implementation. The Twelve-Factor App

Two profiles, one codebase ​

Hosted profile. Replace an API or compute worker while the private Rust store continues to own SQLite and durable artifacts. Verify that sessions, runs, leases, review decisions, and replay cursors survive. The browser connects through one public origin. The store remains private.

Local appliance. On a workstation, an explicitly selected library directory can hold the same domain and storage modules together. This stateful profile trades horizontal scaling and process disposability for portability. Recovery, configuration, backup, and provenance still need direct tests.

A volume is not a magic statelessness switch. The hosted store remains stateful and single-writer per writable library; it needs its own backup/restore contract. We do not mount a live SQLite WAL database over a network filesystem. SQLite documents that WAL processes must operate on the same host. SQLite WAL.

Follow the proposed API replacement through one deployment. Collect all three records for the same run.

  1. TF-05, artifact. Before rollout, compare the digest selected for deployment with the digest that passed QA. Record both identifiers and the deployment configuration revision.
  2. TF-06, recovered session. Record the run ID and last committed cursor, then replace the API process. Reopen the session through the replacement and verify that the private store supplies the same run, citations and checkpoint. Keep the responses from both processes.
  3. TF-09, shutdown. Send the old API a termination signal. Record when it stopped admitting work, the disposition of the active request and whether it exited within the configured grace period. Compare the terminal state with what the replacement serves.

These are acceptance records to collect when a hosted implementation is available.

Configuration contract ​

Proposed runtime variables are granular, validated settings, not a single opaque production switch:

VariableMeaning and boundary
LAB_BIND_ADDR, LAB_PORTHTTP bind location; local defaults may be loopback, container deployment explicitly binds an approved interface
LAB_STORE_URLPrivate store endpoint for hosted API/workers
LAB_LIBRARY_PATHStore/local-authoring process only; never a browser-selected filesystem path
LAB_MODEL_MODEExplicit mock, local or remote; absence is not silent permission to call a provider
LAB_MODEL_ENDPOINTOperator-controlled, allowlisted model service
LAB_MAX_CONCURRENT_RUNS, LAB_MAX_OUTPUT_BYTESPositive bounded limits; parsed on startup
LAB_SHUTDOWN_GRACE_SECONDSGrace budget coordinated with the process supervisor

Secrets use the deployment's credential injection mechanism and are never committed, returned in public configuration or printed. A variable carrying a secret-file reference is a deliberate injection choice, not permission to put its contents into a release manifest.

The Svelte frontend should use relative /api paths and a sanitized runtime configuration endpoint when needed. Environment-specific URLs baked into JavaScript at build time would prevent promoting exactly the same frontend artifact. Public runtime configuration is an allowlist, not a dump of the process environment.

State and release rules ​

The canonical store transaction owns graph changes and their events. The hosted conversation store is operational state, separate from the immutable published research snapshot. No cross-database atomic transaction is assumed: each answer pins an already published library revision and records that reference durably in its own run transaction.

A release manifest records source revision, application artifact digest, schema compatibility range, selected library revision, embedding-space identities and enabled worker/model versions. Configuration fingerprints exclude secret values. A schema-changing release may require a forward repair or a restore; switching an image tag alone is not a safe rollback plan.

Operational logs and the evidence audit ledger are different. Stdout logs support diagnosis; the audit ledger is durable, access-controlled application data and must participate in the relevant transaction and retention policy.

Explicit exceptions and nonclaims ​

The local embedded store does not meet strict stateless-process scaling. The hosted private store is a stateful backing resource, not an API replica. CUDA and Apple implementations need compatible contracts but need not produce bit-identical floating-point output. Multi-architecture images require separately built and tested artifacts; an OCI index alone does not prove parity.

Do not claim twelve-factor compliance because the project uses Docker, Rust or environment variables. Claim each tested property separately. The clean-build plan, examples and roadmap turn these gates into work.
