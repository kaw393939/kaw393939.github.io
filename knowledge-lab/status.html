Status and evidence ​

The student guide is public. The proposed research application has a different status. Here is how to verify which deliverable someone is talking about.

Share on LinkedIn

LinkedIn opens a draft you can review before posting.

Ask one short question before relying on a status claim: which artifact? The published documentation, a synthetic contract lab and a proposed Rust service require different evidence. This page records the reviewed baseline and shows where to verify a release.

Review scope. Software availability and publication are separate claims.

Available in this repository ​

DeliverableScope
VitePress documentationVision, guides, current design, build roadmap and reference library
IS373 student supportOriginal-assignment-aligned guides, AI prompts, checking worksheet and optional local retrieval lab (not a hosted submission)
Ordo source auditExact inspected revisions, reuse decisions and known gaps—not donor test results
Synthetic contract labsSeven Rust, ten JavaScript and eight SQLite/Python tests

Validation and CIPlan traceability, documentation build, links, anchors, assets, sitemap and navigation

Use actual workflow logs for execution results. Lab counts describe the suites; a passing run does not establish the full application's behavior. Example scope.

Not implemented here ​

The research Rust workspace, production schema, plugin host, interactive Svelte research interface, canonical resolution service, durable hosted store and model adapters remain planned. Donor code was not bulk imported; donor runtime suites were not executed by this audit. Native hardware quality, retrieval quality and production capacity remain unmeasured.

Public documentation mirror and project Pages ​

PublicationRelease evidence
Portfolio editionThe public mirror manifest names the Lab source revision. Check it against the portfolio publish run and the lab-docs-revision tag on the lesson you opened.
Standalone Lab PagesOpen the intended commit’s successful deployment in the Lab Documentation workflow. Its deployment URL and HTTPS check identify the standalone build and revision it verified.

Both builds use the Lab repository. A portfolio promotion can lag the standalone release. If an older project URL redirects, identify the edition from its final address and revision marker. Local and public release checks.

Publication is a separate gate ​

For a welcome scaffold build, inspect the Welcome workflow. Registry publication has a separate workflow. A public research application would also need a host deployment receipt and a check of the research service over HTTPS. Application hosting plan.

Which plan takes precedence? ​

Research overview explains intent; Design and Build lead to the current contracts. The authoritative material remains in project/, reuse/ and engineering/. Entry pages summarize and link, not replace it.

The S0–S7 roadmap supersedes the earlier G-series ordering. Older architecture, reviews and research retain visible reference notices. Reuse the historical Rust kernel, repair its gaps, defer a broker, and separate the hosted API from the private stateful store. Local embedded storage remains an explicit twelve-factor exception.

Next implementation gate ​

The next unverified milestone is S0, approval to reuse selected donor code. For one selected job operation, attach the exact donor revision, dependency boundary, reuse decision and characterization results required by A-15. Once that gate passes, S1 calls for a durable job that survives restart and rejects a stale worker result in the application store.
