Run and publish the documentation ​

You fixed a page locally. How do you know your students can read that exact revision? Follow the change through a build, a deployment and the public URL.

Share on LinkedIn

LinkedIn opens a draft you can review before posting.

Edit the textbook in the Lab repository. That repository can publish standalone documentation. The portfolio builds a separately pinned copy from the same files. A change reaches readers of each edition through its own workflow.

Local preview ​

Use Node.js 22+ and Python 3.10+ with SQLite. From a directory where you keep your projects, run:

sh
git clone https://github.com/kaw393939/is373-rag.git
cd is373-rag
npm ci
npm run dev

If you already have the checkout, start in its directory. Open the displayed address with the /is373-rag/ base. Model credentials are unnecessary.

Verify the site ​

Stop the development server, then run:

sh
npm test
npm run preview

Open the changed lesson in the preview and follow its next link. Record git rev-parse HEAD and git status --short in your review so a colleague can identify local edits beyond that commit. A local build normally marks its pages local. The clean-build instructions include the separate Rust exercise.

Standalone project Pages configuration ​

For a new fork or recovery, select GitHub Actions as the publishing source in the Pages settings. In the configured Lab repository, pull requests build previews. The Documentation workflow builds and publishes accepted changes on main. It reads Pages metadata for the deployed origin and base.

What standalone publication verifies ​

Open the successful deployment job for the source commit and follow its reported Pages URL. It checks the public homepage, vision, glossary and a stylesheet. At the final address of the page you edited, inspect the HTML tag named lab-docs-revision and compare its content with the workflow commit. If you land under /knowledge-lab/ through a compatibility redirect, use the mirror check below.

Public GitHub Pages mirror ​

The portfolio edition has its own build script. It checks out an approved Lab commit, sets the base to /knowledge-lab/, validates the generated site and embeds it in the portfolio.

To promote a Lab release, update the revision in the portfolio’s shared release configuration. After its publish workflow succeeds, open the changed lesson at the public address. Compare the revision in the mirror manifest and the page’s lab-docs-revision with the approved Lab commit. The portfolio commit identifies the publishing change.

Ongoing updates ​

Keep one Markdown source in the Lab repository and preserve links to the owning requirements. Release records should identify the final page URL, the Lab revision and the publishing workflow. Documentation editing rules.

Boundaries ​

These workflows publish static teaching materials. The proposed research service has a separate application hosting plan. Use synthetic examples and public source material in documentation and release artifacts.
