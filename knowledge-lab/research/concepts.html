Concept reading guide ​

Sources checked: November 5, 2026. Use this guide to connect the vocabulary in the draft architecture to primary explanations. The links teach mechanisms; they do not establish that a particular product is our final choice. Each annotation identifies why the concept matters and where it appears in our design.

Suggested reading order ​

  1. Start with BM25, vectors, and rank fusion to understand how passages become answer candidates.
  2. Read chunking, NER, linking, and graph search to see how documents become structured evidence.
  3. Study dependencies, retries, messaging, and WAL before deciding how ingestion runs and publishes updates.
  4. Finish with reactivity, SSE, and recovery, then trace one document upload and one interrupted answer through the system overview.

Retrieval foundations ​

BM25 and full-text search ​

Learn here: SQLite FTS5 and its BM25 function. It explains lexical matching and relevance ranking; FTS5 assigns better matches lower scores. Our keyword branch needs this behavior for useful literal matches and correct result ordering. Related: Three retrieval signals.

Exact and approximate vector search ​

Learn here: SQLite Vec1 user manual. Compare exhaustive nearest-neighbor search with trained approximate indexes, filtering, and reranking. Our vector selection must measure eligible-result recall alongside latency rather than assume all semantic indexes behave alike. Related: Vector capability decision.

Reciprocal rank fusion ​

Learn here: Elastic's RRF explanation and formula. RRF combines positions in ranked lists rather than requiring identical score scales. Our initial hybrid baseline can therefore combine keyword and semantic candidates without adding incompatible raw scores. Related: Candidate composition.

Documents and extracted knowledge ​

Structure-aware chunking ​

Learn here: Docling chunking concepts. Study document structure, token budgets, and contextualized chunk representations. Our pipeline needs retrieval-sized passages while preserving parent sections and source locations for extraction and citations. Related: Parsing and chunking.

Named entity recognition ​

Learn here: spaCy's named-entity guide. NER identifies spans and categories in text. Our mention records must preserve those spans separately from canonical identities; detecting a name alone does not resolve which entity it denotes. Related: NLP and entity extraction.

Entity linking and disambiguation ​

Learn here: spaCy EntityLinker. It describes knowledge-base candidates and contextual selection. Our resolver needs stable identifiers, supporting context, and an unresolved outcome so ambiguous names do not force destructive merges. Related: Evidence model.

Local and global graph retrieval ​

Learn here: GraphRAG's local search and global search. Compare entity-focused evidence with corpus-level community summaries. Our design should evaluate these question types separately and keep generated summaries linked to their underlying sources. Related: Claims and augmentation.

Workflow and storage behavior ​

Assets and dependency graphs ​

Learn here: Dagster assets. An asset describes a persistent result and how it depends on other results. This helps model our chunks, embeddings, and claims as versioned outputs with explicit recomputation dependencies. Related: Artifact dependencies.

Retries and durable work ​

Learn here: Temporal retry policies. Read the distinction between workflow logic and failure-prone activities. Our ingestion stages need bounded retry policies and idempotent publication even when execution infrastructure can recover progress. Related: Durable execution contract.

Ephemeral messaging and retained streams ​

Learn here: NATS JetStream concepts. Core messaging and retained, acknowledged streams provide different delivery behavior. Our jobs and replay requirements need deliberate retention and duplicate handling; transient notifications can use lighter delivery. Related: ETL durability.

SQLite WAL and checkpoints ​

Learn here: SQLite write-ahead logging. Readers can overlap a writer, while long read transactions can delay checkpoint progress. Our retrieval transactions should finish before answer streaming, and ingestion must account for the single-writer boundary. Related: SQLite operating boundary.

Frontend and streaming contracts ​

Granular reactive state ​

Learn here: Svelte's reactive state. Read how property changes trigger updates. Our active message, composer, and source panel should have independent state ownership so streaming work does not unnecessarily disturb other interactions. Related: Component ownership.

SSE framing and reconnection ​

Learn here: MDN's server-sent events guide. Study event fields, blank-line framing, identifiers, and reconnection behavior. Our stream decoder must assemble complete events across network reads and distinguish transport reconnection from answer recovery. Related: Event envelope.

Snapshot and replay ​

Learn here: our proposed ordering and recovery invariants and frontend stream lifecycle. This is our application protocol: snapshots carry cursors, retained events support catch-up, and gaps require explicit resynchronization. SSE itself does not provide event retention or restore failed model inference.
